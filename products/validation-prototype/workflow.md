# Maintenance Request-to-Resolution Workflow

*One-page validation prototype — a lightweight handoff model to discuss with property managers. It is not a policy, emergency procedure, or finished product.*

## 1. Receive and capture

Record the requester, property/unit, location, issue description, access constraints, and when/how to contact them. Create or link the request in the property’s system of record and assign a ticket ID. Ask for clarification if the issue or location is unclear.

## 2. Triage and decide next action

Review impact and urgency using the property’s existing priority and emergency rules. Record the decision, owner, next action, and next update time. Do not let a tracker replace the property’s escalation procedure.

## 3. Dispatch and coordinate

Send the vendor/technician the ticket ID, issue and location, access details, relevant observations, requested scope, and update expectations. Confirm estimate and approval requirements before authorizing work. Track appointment, access, and approval status.

## 4. Track until resolved

Keep one current status: **New → Triage → Waiting for information/approval → Scheduled → In progress → Complete**. For every wait, record what is pending, who owns the next step, and when to follow up. Log dated updates in the work order.

## 5. Verify and close

Capture findings, work performed, cost/approval records, and supporting documentation. If unresolved, keep the ticket open or in a pending status with the next owner/date. Update the appropriate contact and record any confirmation or return visit.

## Validation questions

Does this match the manager’s actual workflow? Which handoff, field, or status is missing or redundant? Is this already handled well in their property-management software? Would a separate reusable form/tracker create value, or would it duplicate records? Test the workflow with real examples before expanding it.
